# Architecture, data and repo rules (mandatory for every team)

These rules apply to every project a team builds or changes, whether or not the
user asks. Left alone, agents write flat code: handlers that query the database,
one folder mixing every concern, the same type declared five times, money as
floats, statuses as free strings, business rules copied into the UI. The PM
enforces these rules from the first builder on, and the critic blocks any branch
that breaks them.

## Before the first builder
- Decide the architecture first and write it in `docs/ARCHITECTURE.md`: the
  layers, the feature modules, the canonical types and how each rule below is
  enforced in this project. Builders read it before coding.
- Turn the dependency rules into a check that fails CI before feature code lands
  (an import or boundary linter, or an architecture test). A rule only written
  in prose will be broken.
- On an existing codebase that breaks these rules: record the target, list
  today's violations as a baseline that may only shrink, and require that new
  code follows the target and touched code moves to it. Never add flat code
  because the old code is flat.

## Structure
- Organise by feature module first, then by layer inside each module. Never one
  folder per technical kind for the whole app.
- Separate layers inside each module: domain (types and pure rules, no I/O),
  application (use cases, transactions, authorization, ports), infrastructure
  (database, external services), and the entry layer (HTTP routes, jobs, CLI).
- Dependencies point inward only: entry calls application, application uses
  domain, infrastructure implements application ports. Domain imports no
  framework, database client or other layer.
- Entry points stay thin: parse the input, call one use case, map the result or
  error. No queries, no business rules, no cross-module logic in a route, server
  action, job handler or component.
- Modules talk to each other only through their application interface, never
  through each other's tables or repositories.

## Frontend and backend separation
- The backend owns business rules, authorization, validation of record and all
  persistence. The frontend owns presentation and interaction.
- The frontend never decides a rule that matters (prices, money, permissions,
  state transitions, eligibility). It shows what the API returns, or uses rule
  data the backend publishes. Client-side checks are for convenience only and
  the backend repeats them.
- In full-stack frameworks the same split holds: server files call backend use
  cases; components never import the database or business services.
- The frontend has its own layers too: types, application state and use cases,
  API adapters that decode responses, and presentation. Components do not call
  fetch directly or reshape raw payloads.
- Business data lives behind the API. Browser storage holds UI conveniences only.

## Data types
- One canonical type per business concept, defined once in the domain and
  imported everywhere else. A second declaration of the same shape is a defect.
- Parse every input once at its boundary (HTTP, forms, database rows, storage,
  third-party responses, environment) into canonical types with a schema
  validator. Raw JSON, untyped dicts and `any` never travel past the boundary.
- Frontend types are generated from the backend schema, or tested against shared
  example payloads, so the two sides cannot drift.
- Money is integer minor units or a decimal type, always with its currency,
  never a float. Rounding happens in one named function.
- Instants are stored in UTC with a time zone; calendar dates are dates; the
  user's time zone is applied only for display.
- Ids are plain UUIDs or native database ids, with no type prefixes. People see
  human-readable numbers, generated by the database.
- Closed sets (statuses, roles, currencies) are enums in code plus a database
  constraint, with transitions in one function. Business vocabularies that
  admins may change are seeded, editable tables referenced by foreign key, not
  enums and not free text.
- Identifiers, files, tables and columns use one language (English by default).
  User-facing text lives only in translation files.

## Data storage
- Typed columns, `NOT NULL` by default, foreign keys, unique and check
  constraints for every invariant the database can hold.
- No JSON columns for data that is queried, filtered, joined or validated. JSON
  is only for opaque payloads.
- One source of truth per fact. Derived values are computed, or kept as a
  projection with a test proving it matches the source.
- Every schema change is a numbered migration, tested on a seeded database, with
  a downgrade or an explicit guard.
- History that matters (prices, roles, money) goes in audit or revision tables,
  not in overwritten columns.
- Seed data is synthetic and created through the app's own use cases. Before
  launch, reseed instead of writing compatibility code for old shapes.
- Rules that drive money or permissions live in one central service configured
  from typed tables, never duplicated.

## Contracts
- Every API shape has a schema and an example payload file. Producers test
  against it, consumers mock from it.
- One error shape for the whole API, mapped from domain errors at the entry layer.
- Authorization follows a written role matrix, with an API test for every role,
  the forbidden cases included.

## Keep the repo clean
- No dead code, commented-out blocks, unused exports, stale feature flags or
  "v2" copies left next to the old version. When something is replaced, the old
  one is deleted in the same phase.
- No scratch files, screenshots, logs, reports, dumps or generated output
  committed outside their agreed folders; keep them in `.gitignore`.
- One way to do each thing: one HTTP client, one validator, one date library,
  one migration tool, one test runner per side. Adding a second needs a recorded
  decision.
- Files and names follow one convention per kind, set in the architecture doc.
  Tests live next to their code or in one agreed tree, not scattered.
- Documentation describes the code as it is. Update it in the same branch, and
  move outdated plans to an archive folder.
- Worktrees and branches are removed once merged. No secrets, env files or real
  personal data in the repo, fixtures or reports.

## Review gate
The critic checks every branch against this file. Code in the wrong layer, a
duplicated type or rule, an unparsed input, a business rule in the frontend,
a missing constraint or migration test, float money, queryable JSON, or leftover
dead code is a NO-GO (P2 or higher), whatever the tests say.

## Rules block for briefs
Paste this into the shared brief and every builder brief:

```text
Architecture rules (mandatory, see docs/ARCHITECTURE.md):
- Feature modules, layered inside: domain, application, infrastructure, entry.
  Dependencies point inward; CI enforces it. Entry points only parse, call one
  use case and map the result.
- Backend owns rules, authorization, validation and persistence. Frontend shows
  and interacts; it never decides money, permissions or state transitions.
- One canonical type per concept, defined once. Parse every input at its
  boundary; no raw JSON or any. Frontend types come from the backend schema.
- Money: minor units or decimal plus currency, never float. UTC instants, dates
  as dates. Plain UUID ids. Enums plus DB constraints for closed sets; editable
  seeded tables for business vocabularies.
- Tables: NOT NULL, FKs, unique and check constraints, no queryable JSON,
  numbered and tested migrations, one source of truth.
- Keep the repo clean: delete what you replace, no dead code, no stray files,
  one tool per job, docs updated in the same branch.
```
